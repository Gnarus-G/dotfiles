# Research basis and reading guide

Sources below are primary papers, original authors' articles, or implementers' documentation, checked for the stated claims on 2026-10-17. They motivate the technique; none proves that a particular implementation is correct.

## Foundations and academic evidence

1. **G. H. Mealy, “A Method for Synthesizing Sequential Circuits,” *Bell System Technical Journal* 34(5), 1955**, [publisher](https://www.nokia.com/bell-labs/publications-and-media/publications/a-method-for-synthesizing-sequential-circuits/), [DOI](https://doi.org/10.1002/j.1538-7305.1955.tb03788.x). Foundational formal model of sequential circuits with memory, inputs, transitions and outputs; motivates specifying output as a function of state and input. Our software effect intents are a design adaptation, not a claim that this paper covered network I/O.
2. **D. Harel, “Statecharts: A Visual Formalism for Complex Systems,” *Science of Computer Programming* 8, 231–274, 1987**, [paper](https://www.state-machine.com/doc/Harel87.pdf). Reactive systems need event/state specifications; hierarchical and orthogonal states address flat-state explosion. Use these features for genuinely interacting submachines, not a diagram per function.
3. **L. Lamport, “Time, Clocks, and the Ordering of Events in a Distributed System,” *Communications of the ACM* 21(7), 558–565, 1978**, [author-hosted paper](https://lamport.org/pubs/time-clocks.pdf), [DOI](https://doi.org/10.1145/359545.359563). Causal “happened-before” is a partial order; physical timestamps do not by themselves establish causation. Drives per-owner sequence numbers, correlation and explicit treatment of concurrency.
4. **J. Hughes, “Experiences with QuickCheck: Testing the Hard Stuff and Staying Sane,”** [paper](https://www.cs.tufts.edu/~nr/cs257/archive/john-hughes/quviq-testing.pdf). Describes industrial state-machine testing of C/embedded and concurrent Erlang software using generated command sequences, model preconditions/postconditions and shrinking; the model can itself be wrong. Use for testing transitions and recovery sequences, not as a replacement for adapter/end-to-end tests.

## Implemented styles, including non-FP approaches

5. **E. Czaplicki, *An Introduction to Elm*: “Commands and Subscriptions,”** [official guide](https://guide.elm-lang.org/effects/). The Elm runtime maps outside-world events to messages and executes `Cmd`/`Sub` values returned by program logic. A concrete instance of data-described effects; a Rust/OO program can implement the boundary without adopting Elm.
6. **G. Bernhardt, “Boundaries” (SCNA 2012),** [author's talk page](https://www.destroyallsoftware.com/talks/boundaries). Value-based subsystem boundaries and the functional-core/imperative-shell approach make decisions separately testable from effects. The page describes the talk and links the related screencast; do not attribute specific unviewed screencast details to it.
7. **Erlang/OTP `gen_statem` reference**, [official documentation](https://www.erlang.org/doc/apps/stdlib/gen_statem.html). A production non-Elm pattern: events are dispatched to callbacks by state, callbacks return next state/data and ordered transition actions, with timeouts, postponement, tracing, and supervision. Runtime actions are not by themselves a durable external-effect journal.
8. **M. Fowler, “Event Sourcing” (2005),** [author's article](https://martinfowler.com/eaaDev/EventSourcing.html). Event logs can reconstruct application state; external queries need recorded responses and replayed events must not re-send external updates. Event sourcing is one possible persistence choice, not a prerequisite for an event-to-action reducer.
9. **C. Richardson, “Transactional Outbox,”** [pattern by the implementer](https://microservices.io/patterns/data/transactional-outbox.html). Atomically save a database update and outbound message intent, then relay; the relay may publish twice, so consumers need idempotence. Applies to DB-to-message publishing, not an exactly-once guarantee for browser clicks.
10. **Temporal, “Workflow Execution overview,”** [official documentation](https://docs.temporal.io/workflow-execution). Workflow commands are checked against event history during replay; activities carry environmental interactions. Useful when durable workflow progress is already provided, but a retried external activity can still have an ambiguous result.
11. **OpenTelemetry, “Tracing API,”** [specification](https://opentelemetry.io/docs/specs/otel/trace/api). Spans have trace/span identity, links, events, timestamps and status; correlate diagnostics across boundaries. Sampling/no-op SDK behavior makes traces unsuitable as the only authoritative state or recovery record.

## Synthesis and cautions

Mealy/Harel explain the state + event -> transition/output shape; Elm/`gen_statem` show different runtimes can execute returned actions; Bernhardt motivates separating the decision boundary; Hughes shows how to test stateful interactions; Lamport explains why ordering/correlation matters; Fowler/Richardson/Temporal establish what durable histories can and cannot recover; OpenTelemetry supplies diagnostic correlation rather than authority. The specific `decide(state, event) -> (next_state, intents)` recipe and the unknown-outcome/reconciliation workflow are a synthesis for effectful software, not a direct quotation or universal guarantee from any one source.
