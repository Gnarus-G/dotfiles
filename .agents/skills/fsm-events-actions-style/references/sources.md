# Research basis and reading guide

Sources below are primary papers, original authors' articles, or implementers' documentation, checked for the stated claims on 2026-10-17. The four academic papers below were read in full (Mealy and Harel via OCR of scanned PDFs); OCR of equations and diagrams is imperfect, so the notes rely on the accompanying prose and section context. They motivate the technique; none proves that a particular implementation is correct.

## Foundations and academic evidence

1. **G. H. Mealy, “A Method for Synthesizing Sequential Circuits,” *Bell System Technical Journal* 34(5), 1955**, [full paper](https://ia801605.us.archive.org/3/items/bstj34-5-1045/bstj34-5-1045.pdf), [publisher](https://www.nokia.com/bell-labs/publications-and-media/publications/a-method-for-synthesizing-sequential-circuits/). §§2–3: present state + input uniquely determine next state and output; states are equivalent only if **no future input sequence** distinguishes their output sequences. §4.4: blanks/“don't cares” in a partial specification permit non-equivalent completions, so unspecified inputs need an explicit contract. §§4.5–5: fewer states/storage elements do not necessarily mean cheaper, faster, or more reliable physical implementation; asynchronous coding introduces races. These are hardware results, not a proof that software reducer intents make external effects deterministic.
2. **D. Harel, “Statecharts: A Visual Formalism for Complex Systems,” *Science of Computer Programming* 8, 231–274, 1987**, [full paper](https://www.state-machine.com/doc/Harel87.pdf). §§2–3: hierarchical states and orthogonal components avoid flat diagram blow-up and express independent behavior. §5 distinguishes instantaneous transition **actions** from long-running **activities**; §§7–8 show that simultaneous events, generated internal events, and broadcast cycles make semantics subtle. This motivates an explicit event/step/ordering rule rather than automatically adopting every statechart feature; §6 labels several extensions preliminary.
3. **L. Lamport, “Time, Clocks, and the Ordering of Events in a Distributed System,” *Communications of the ACM* 21(7), 558–565, 1978**, [full paper](https://lamport.org/pubs/time-clocks.pdf), [DOI](https://doi.org/10.1145/359545.359563). “The Partial Ordering” and “Logical Clocks”: happens-before is a partial order of process order, message order and transitivity; logical clock order's converse does not follow. “Ordering the Events Totally” extends it with an arbitrary tie-break and assumes reliable communication for the illustrated state-machine synchronization. “Anomalous Behavior”: externally known order is lost unless explicitly supplied; synchronized physical clocks can help only under stated clock/transmission assumptions. Hence correlate causal IDs/sequence within owners; do not infer causality from wall time alone.
4. **J. Hughes, “Experiences with QuickCheck: Testing the Hard Stuff and Staying Sane,”** [full paper](https://www.cs.tufts.edu/~nr/cs257/archive/john-hughes/quviq-testing.pdf). §2 derives model preconditions, next-state functions and postconditions, then finds both mistaken preconditions and code bugs; an omitted `size` operation was **never tested** despite passing tests. §§3–4 describe real CAN/dets faults and shrinking, including database corruption found only by a separate post-run invariant when operation results looked plausible; concurrency testing searches for some legal interleaving after sequential agreement. Use independent requirements, coverage and external invariants alongside generated transition sequences; this paper is an experience report, not a formal guarantee.

## Implemented styles, including non-FP approaches

5. **E. Czaplicki, *An Introduction to Elm*: “Commands and Subscriptions,”** [official guide](https://guide.elm-lang.org/effects/). The Elm runtime maps outside-world events to messages and executes `Cmd`/`Sub` values returned by program logic. A concrete instance of data-described effects; a Rust/OO program can implement the boundary without adopting Elm.
6. **G. Bernhardt, “Boundaries” (SCNA 2012),** [author's talk page](https://www.destroyallsoftware.com/talks/boundaries). Value-based subsystem boundaries and the functional-core/imperative-shell approach make decisions separately testable from effects. The page describes the talk and links the related screencast; do not attribute specific unviewed screencast details to it.
7. **Erlang/OTP `gen_statem` reference**, [official documentation](https://www.erlang.org/doc/apps/stdlib/gen_statem.html). A production non-Elm pattern: events are dispatched to callbacks by state, callbacks return next state/data and ordered transition actions, with timeouts, postponement, tracing, and supervision. Runtime actions are not by themselves a durable external-effect journal.
8. **M. Fowler, “Event Sourcing” (2005),** [author's article](https://martinfowler.com/eaaDev/EventSourcing.html). Event logs can reconstruct application state; external queries need recorded responses and replayed events must not re-send external updates. Event sourcing is one possible persistence choice, not a prerequisite for an event-to-action reducer.
9. **C. Richardson, “Transactional Outbox,”** [pattern by the implementer](https://microservices.io/patterns/data/transactional-outbox.html). Atomically save a database update and outbound message intent, then relay; the relay may publish twice, so consumers need idempotence. Applies to DB-to-message publishing, not an exactly-once guarantee for browser clicks.
10. **Temporal, “Workflow Execution overview,”** [official documentation](https://docs.temporal.io/workflow-execution). Workflow commands are checked against event history during replay; activities carry environmental interactions. Useful when durable workflow progress is already provided, but a retried external activity can still have an ambiguous result.
11. **OpenTelemetry, “Tracing API,”** [specification](https://opentelemetry.io/docs/specs/otel/trace/api). Spans have trace/span identity, links, events, timestamps and status; correlate diagnostics across boundaries. Sampling/no-op SDK behavior makes traces unsuitable as the only authoritative state or recovery record.
12. **Effect, v4 documentation**, [creating effects](https://effect.website/docs/v4/getting-started/creating-effects/), [runtime](https://effect.website/docs/v4/runtime/), [tracing](https://effect.website/docs/v4/observability/tracing/). `Effect.tryPromise` wraps potentially rejecting I/O, `Effect.runPromise` runs an effect, and `Effect.withSpan` traces it. Effect is an optional TypeScript interpreter for this design, not an application event journal or a guarantee of exactly-once external effects; see [typescript.md](typescript.md).
13. **M. Thompson et al., “LMAX Disruptor: High performance alternative to bounded queues for exchanging data between concurrent threads” (2011)**, [technical paper](https://lmax-exchange.github.io/disruptor/disruptor.html), [implementers' guide](https://lmax-exchange.github.io/disruptor/user-guide/). §§2–3 separate slot storage, sequencing and publication; describe single-writer ownership, preallocation, bounded ring capacity, batching, cache effects and consumer dependency gating. The guide notes producer overrun and busy-spin/CPU tradeoffs. Benchmark figures are platform-specific, not a promise for Rust or JS.
14. **Rust standard library, `GlobalAlloc`**, [official documentation](https://doc.rust-lang.org/std/alloc/trait.GlobalAlloc.html). Global allocator instrumentation can miss optimized-away or merged allocations, so validate the exact claimed boundary with profiles and optimized-build checks as well as source review; see [hot-path.md](hot-path.md).
15. **Erlang/OTP, “Processes,”** [official reference](https://www.erlang.org/doc/system/ref_man_processes.html). Processes have mailboxes and exchange asynchronous signals; delivery order is guaranteed for multiple signals from the same sender to the same destination, but distributed signals may be lost. Combined with `gen_statem` above, this illustrates actor-local serialization and explicit state transitions, not universal delivery or durability guarantees; see [actors.md](actors.md).
16. **Akka, “How the Actor Model Meets the Needs of Modern, Distributed Systems,”** [implementers' guide](https://doc.akka.io/libraries/akka-core/current/typed/guide/actors-intro.html). Actors process one message at a time while independent actors run concurrently; replies and failures cross actor boundaries as messages. This motivates actors as independent state owners, not as a requirement for every state machine; see [actors.md](actors.md).

## Synthesis and cautions

Mealy/Harel explain the state + event -> transition/output shape and why partial rules or generated events need precise semantics; Elm/`gen_statem` show different runtimes can execute returned actions; Erlang/Akka show actors as serial owners that can run concurrently; Bernhardt motivates separating the decision boundary; Hughes shows how to test stateful interactions and test coverage; Lamport explains why ordering/correlation matters; Fowler/Richardson/Temporal establish what durable histories can and cannot recover; OpenTelemetry supplies diagnostic correlation rather than authority; LMAX supplies performance techniques when measurements warrant them. The specific `decide(state, event) -> (next_state, intents)` recipe and the unknown-outcome/reconciliation workflow are a synthesis for effectful software, not a direct quotation or universal guarantee from any one source.
